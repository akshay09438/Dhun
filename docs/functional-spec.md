# Prompt-DJ — Functional Spec (V1)

_What the app does, for the user, screen by screen. Approved during discovery on 2026-07-05. This is a living document — kept true to the code. The "how it's built" lives in [technical-spec.md](technical-spec.md); progress lives in [implementation-plan.md](implementation-plan.md)._

> **LATEST — 2026-08-15 (YOUR SETS STOP COMING OUT THE SAME, and everything is switched on; branch `fix/discord-set-variety`).** **Nothing about how a mix SOUNDS changed** — the mixing engine and the quality referee were not touched. **(1) EVERY SET YOU BUILT IN DISCORD CAME OUT IN THE SAME STYLE ORDER, FOREVER.** There are three mixing styles — plain, chopped, echoey. Inside one grind they were always well varied: ask for three and you got all three, never two the same next to each other. But the shuffle was never reshuffled between grinds, so your 1st, 2nd and 10th set of five all played **plain → chopped → echoey → chopped → echoey**, every session, for as long as you used it. The website already reshuffled properly; Discord never did. **Now each grind gets a fresh shuffle** — checked over 200 grinds in a row: never the same order twice running, and it works through all 18 possible orders for a set of five. **(2) A BIGGER ONE FOUND WHILE FIXING IT: the 🔁 Again button on a multi-song grind did NOTHING.** Because the styles never changed, the app recognised the result as something it had already made and handed you back **the exact same audio file**, presented as a new take. Pressing Again on a set was a no-op. It now genuinely re-rolls. _(Again on a SINGLE-song grind was always fine — that path already rotated correctly.)_ **(3) THE HONEST CEILING, so it is never mistaken for a bug: there are only three styles.** A set of four or five MUST reuse one — there is no fourth style in existence. What is guaranteed is that a repeat never lands next to itself, and that every set of five is one style once and two styles twice. Five genuinely different styles would mean **building a fourth and fifth rule**, which is real work, not a setting. **(4) AND FIVE BEATS ONLY GET TWO STYLES.** Lean On, Wake Me Up, Faded, Closer and Confusion sing their own line before handing over, and the chopped style would throw that line away — so a set built only from those alternates plain → echoey → plain. Deliberate protection, not a fault. **(5) EVERYTHING IS LIVE.** The mixing engine, the DJ console, the dev dashboard at `/#dev` and Grinder are all running. Grinder is logged in with all 9 commands registered and correctly hidden-or-visible, and **the second voice came online**, so two listening rooms can have sound at the same time. Nine channels, untouched. **(6) NOT DONE, and you decided this: first-time song pairs still take 50–70 seconds**; a pair you have used before takes 17–20. _(Founder `/zuko:build` 2026-08-15.)_

> **LATEST — 2026-08-14 (YOUR OWN MARKS NOW REACH THE APP FOR 103 MORE SONGS; branch `feat/wire-hand-marks`).** For a long time the founder's marking sheet (`scripts/song_marks.csv`, filled in via `scripts/mark_drops.html`) was **a record that nothing read** — a mark did not change a single mix until somebody hand-copied it into the app. Measured 2026-08-14: **410 marks made, 40 actually wired.** About nine marks in ten were doing nothing. **(1) THAT GAP IS CLOSED, MECHANICALLY.** Every mark for a song the app has loaded is now wired in — **hooks 26 → 129, marked drops 9 → 133** — so where you said the drop is, the vocal's signature line now lands, instead of the app guessing. This matters most where the guessing was worst: automatic drop detection was measured at **~36% precision** (on Wake Me Up it found 7 drops when 2 were real), and your ear-marks replace that rather than adding to it. **(2) NOTHING THAT ALREADY WORKED WAS CHANGED.** Founder's instruction: _"A similar pattern has to be followed for this. Nothing, no single thing, has to change."_ For **8 songs** (Tere Bina, Tere Bin, With You, Nadan Parinde, Faded, Closer, Wake Me Up, Uff Teri Ada) the sheet points at a _different_ part of the song from what is already tuned in the app — 7 to 50 seconds away. **Every one of those keeps its existing, ear-confirmed value.** The wiring only fills in songs that had nothing. That is enforced structurally, not by memory: the hand-marked tables are consulted first and always win, so a future re-run can never retune a song that already sounds right. **(3) MARKS ARE NOW TIED TO THE SONG, NOT THE FILENAME.** The sheet keys marks by file name, which silently detaches when a file is renamed or saved twice — measured the same day, three songs _looked_ unmarked purely because the same audio also existed under a second name. Marks are now matched by the audio itself, so renaming a file cannot separate a song from its marks. **(4) 45 MARKED SONGS ARE STILL WAITING** — they are marked but have never been loaded into the app (mostly the Hindi batch), so their marks stay inert until the song is loaded. **Nothing about how a mix is rendered changed** — the engine and the quality referee were not touched.

People still sitting in the lobby unapproved are not counted either, because they are not in. **(4) IT RE-OPENS IF PEOPLE LEAVE** (founder decision, taken against the recommendation of a one-way switch). The number is tracked live. The honest consequence, so it is never mistaken for a bug: somebody who filled the form and is waiting can watch a newcomer stroll in free after a member leaves. **(5) NOBODY WAITING IS EVER AUTO-APPROVED** (founder decision). Guessing "open" there would hand `@Member` to every stranger arriving in that window. The door is **OPEN** — a newcomer walks straight in. **Grinder must be running for that to happen**; while the bot is off, an arrival simply waits in the lobby until it is back. > **2026-08-13 (THE DOOR: Grinder becomes invite-only, and the founder picks the first 50; branch `feat/the-door`). BUILT BUT NOT SWITCHED ON — the live server is untouched until a separate, deliberate step.** **(1) NOTHING CHANGES ABOUT YOUR SERVER UNTIL ONE SCRIPT IS RUN.** With no door configured the feature is dormant and the server behaves exactly as it does today. Closing the door is `scripts/lock_the_door.py`, which is a dry run by default, prints every change before making it, and asks you to type "yes". **(2) A NEWCOMER SEES ONE ROOM.** `#the-door` says what Grinder is, that the room is small on purpose, and offers one button: **Ask to join**. Everything else is invisible until they are let in. **(3) FIVE QUESTIONS, THE FOUNDER'S OWN:** their name, their relation to music, what AI tools they have used, why they want to join, and what they expect. Discord allows exactly five short questions, so all five fit with nothing dropped. **(4) YOU CHOOSE FROM A POOL — YOU DO NOT APPROVE A QUEUE.** This is the decision that shapes the whole feature. Applications pile up and stay readable side by side: **`/applications`** shows everyone waiting, and **`/applications suno`** (or `dj`, or `midjourney`, or any word) narrows the pile to whoever mentioned it. That is the founder's _"I want to spot them"_ made mechanical. Approving cards as they arrived would have been first-come-first-served wearing a review flow — by the time a good application appeared, the seats would be gone. **(5) FIFTY SEATS, and every card shows how many are left.** At 50 the Approve button warns and asks again rather than refusing; the number is the founder's. Applications keep arriving after 50, so a second wave starts with a queue of good people rather than from zero. **(6) "NOT NOW" NEVER KICKS ANYBODY.** They stay in the lobby and can be approved later. A kick is irreversible and reads as a verdict. **(7) GRINDER NEVER JUDGES AN APPLICANT** — no score, no ranking, no "this one looks promising". Searching for a word the founder typed is a filing cabinet; an opinion shown before their own read would poison it. Same rule as no card ever judging a mix, and it has its own test. **(8) THE EMAIL IS COMPULSORY, AND IT IS QUESTION 2.** Founder decision after seeing the form: it is how you reach somebody whose Discord DMs are shut. Discord allows exactly five boxes and five were already used, so **"What you expect" was dropped** — the founder's choice, because it overlapped almost entirely with "why you want to join" and in practice both got the same sentence. A typo like `akshay at gmail` is warned about rather than rejected: refusing would throw away the four answers already typed, and re-applying replaces the old application rather than adding a second. **(9) WHILE THEY WAIT, THEY HEAR A REAL MIX.** The confirmation carries a link to an actual Grinder track, because between applying and being approved a person can see no channel, hear no room, and watch nobody else grind — a mix they can play is the only thing standing between "I am waiting for something good" and "I filled in a form and nothing happened". It deliberately promises **no timeframe**; it says a human reads every one. **(10) PEOPLE YOU KNOW CAN SKIP THE FORM ENTIRELY — `/invitefriend`.** It hands you a private, **one-use** link. Your friend clicks it and is straight in: no lobby, no questions, no waiting. One use on purpose, because a vouch is for one named person and a link that keeps working is a hole that widens every time it is forwarded. If the bot cannot work out which link somebody used — two people arriving in the same second, say — that person meets the door like anybody else, which is the safe way to be wrong. **(11) HONEST, AND IMPORTANT: this does NOT stop mixes failing under load.** Fifty approved people can still all grind at once; the engine builds 8 at a time and the rest fail rather than wait. That is the render waiting list, still unbuilt. The door controls **who**, not **how many at once**. Full reasoning: [door-policy-design.md](door-policy-design.md). _(Founder decisions 2026-08-13.)_

> **LATEST — 2026-08-13 (WALKING INTO A LISTENING ROOM NO LONGER ANNOUNCES YOU; branch `fix/no-room-join-messages`).** The founder's words: _"no notification should go when a person or any individual joins a Bollywood house or a Hollywood house, because people can automatically see people in their room. Nothing is posted anywhere when somebody joins or leaves a room. **(2) Why it was so much worse than it looks.** The notes were supposed to be throttled — announce the first arrival, then only every third — but **the counter reset to zero every time the room emptied**. So one person stepping out and coming back was announced as if they were the first person in the room, over and over. Testing a room a few times produced a wall of them. Discord's own member list already shows who is sitting in a voice room, so the line never said anything the screen wasn't already saying. **(3) What is deliberately KEPT: Grinder still records who listened and for how long.** The announcement and the record-keeping happened at the same instant but are different jobs, and only the talking was removed — listening time and drop-off are one of the two things the notes list as blocking the community phase, so deleting the wrong half would have quietly cost the founder the measurement they most need. A test now fails if either the noise comes back or the recording goes away. **(4) THE "⚫ Nobody is listening right now. Somebody go start something." CARD IS ALSO GONE** (founder request, same session). It was supposed to be a single sign the bot kept updating in place — but the bot only remembers which message that is _while it is running_, so every restart lost track and posted a brand-new one, and the channel collected a column of identical grey cards. It is deleted rather than fixed, because an empty room is the normal state and a sign announcing it is nagging rather than useful. **The "🔴 SOMEONE IS LISTENING" sign stays** — that one tells you something is actually happening — and when the last person leaves it is now **taken down** rather than swapped for the quiet card, so a stale "someone is listening" can never sit over an empty room. _(Founder request 2026-08-13.)_

> **LATEST — 2026-08-13 (the app tidies up after itself, the best mixes are protected for good, and a download that quietly saved a broken file is fixed; branch `feat/stale-render-cleanup`).** **Nothing about how a mix SOUNDS changed** — the mixing engine and the quality referee were not touched. **(1) FINISHED MIXES NOBODY HAS PLAYED IN A WEEK NOW CLEAR THEMSELVES OFF THE DISK.** Until now the app only ever tidied up when the machine was already in trouble; there was no routine housekeeping at all, so old mixes piled up until they became an emergency. Now, once a minute, anything finished that nobody has played for seven days quietly goes. **Your original songs, the paid-for separated parts, and the analyses can never be touched** — the tidy-up only recognises five kinds of throwaway file, only at the top level, and anything it does not recognise is kept. **(2) ANYTHING PINNED TO #best-mixes IS NEVER REMOVED — EVER** (founder rule, 2026-08-13: _"the mixes which will be in the best mixes tab should not be removed, and other than that, everything should be removed"_). Hitting 📌 now does two things: it posts the mix to the showcase as before, and it permanently protects the original full-quality file on disk. It is protected from the routine weekly tidy-up **and** from the emergency clean-up that runs when the machine is full — "should not be removed" was read as absolute. Two things this fixes that were genuinely broken: the high-quality master of a showcased mix used to be deleted like any other, and **once a mix had been tidied away you could no longer pin it at all**, because pinning re-reads the file off the disk. **(3) THE SEVEN DAYS COUNTS FROM WHEN A MIX WAS LAST PLAYED, NOT FROM WHEN IT WAS MADE** (founder decision). Playing a mix resets its clock, so one you keep coming back to never disappears — only genuinely forgotten ones do. **(4) "DOWNLOAD FULL MIX" NO LONGER SAVES YOU A BROKEN FILE IN SILENCE.** If the mix was not there any more, the button saved a `.wav` that was really an error message in disguise — it simply would not play, and nothing on screen said why. It now tells you plainly that the mix needs making again. This bug existed before today; routine cleanup would have turned it from a rarity into the normal experience of coming back to an old mix. **(5) A CHANGE THAT HAD ALREADY BEEN APPROVED WAS THROWN AWAY RATHER THAN APPLIED.** A card written on 11 Aug argued cleanup started far too late (only under 2 GB free, already inside the zone where mixes fail). True when written — and a different piece of work solved it thirteen hours later with a smarter safeguard that checks whether deleting would even help. **The lesson recorded: an approval has a shelf life.** **(6) What you will notice: nothing.** Mixes you actually use stay instant, and the first run on the founder's machine would have deleted **zero files** — though that number proves less than it sounds, because on this disk-starved machine the emergency clean-up already keeps the folder permanently young, so no week-old mix has ever existed on it to test against. _(Founder `/zuko:build` 2026-08-13.)_

> **LATEST — 2026-08-12 night 3, part 2 (NOTHING STARTS BY ITSELF ANY MORE, and two Grinders can no longer end up in one room; branch `feat/second-grinder-voice`).** Both from the founder testing the second voice live. **(1) THE STATION IS GONE, by founder decision.** A room used to replay past mixes when its waiting list emptied, and walking into a quiet room started one. It was built on 2026-08-12 to stop rooms feeling dead; used for real, it meant **music appearing that nobody had asked for**, in a room the founder was trying to control. Removed completely — the code and its tests. **A room now plays what somebody asked for, and nothing else.** `/grind` starts music. `/play` does exactly one job: pick up whatever `/stop` paused; with nothing paused it says so rather than inventing something. Cause: a Grinder's **claim** on a room and its **seat** in the room were two different lifetimes. Letting go of a room handed back the claim but left the identity sitting there, and the next identity to legitimately claim that room was walked in on top of it. Letting go now means **leaving**. **(3) A second bug from the same session:** a room with no music of its own was reading the _other_ room's speaker, so `/play` in one room could answer about the other room's music. Fixed; three tests written first, all three failed for the right reason. _(Founder session 2026-08-12.)_

> **LATEST — 2026-08-12 night 3 (TWO ROOMS CAN HAVE MUSIC AT THE SAME TIME; branch `feat/second-grinder-voice`).** **Nothing about how a mix SOUNDS changed** — the mixing engine and the quality referee were not touched, and this adds **no** mix-making capacity (that is a separate, agreed next job). **(1) THE WALL, STATED PLAINLY.** A Discord bot application holds ONE voice connection per SERVER — not one per room. So while `#Bollywood_House` was playing, `#Hollywood_Blends` was silent; and worse, when a mix made in the second room reached the front of the queue, Grinder **walked out** of the room it was in — leaving those people in silence — to serve one person next door, then walked back three minutes later. Both rooms got a broken, stop-start night. Measured: the median mix runs **3 min 09 s**, so five people waiting meant the last one waited about **thirteen minutes**, while the engine had finished building their mix in about thirty seconds. It was never a speed problem. **(2) THE ONLY FIX IS MORE IDENTITIES, AND THEY ARE FREE.** Discord lets you create as many bot applications as you like; each one is a separate login that can hold its own room. Grinder now logs the extras in alongside itself. **(3) EACH ROOM IS A FULL, EQUAL ROOM** (founder decision): a mix made in it plays in it immediately, and it has its own waiting list, its own `/skip`, its own `/stop`, its own `/play` and its own station when it falls quiet. Skipping in one room cannot touch the other. **(4) THE EXTRA IS AN IDENTICAL TWIN** (founder decision): same name, same "# GRINDER" disc — applied from code, so there is nothing to do by hand — and it never handles a command or posts anything. Somebody in the second room just sees Grinder; the community never learns there are two. **(5) WHEN EVERY VOICE IS BUSY, THE PERSON IS TOLD** — "waiting for a free voice, 2nd in line" — instead of staring at "grinding…", assuming it broke, and pressing again. **(6) A ROOM THAT EMPTIES KEEPS ITS VOICE FOR ABOUT A MINUTE** (founder decision), so stepping out for twenty seconds does not kill the music; after that the seat goes to whoever needs it. **(7) NOTHING CHANGES UNTIL A TOKEN IS PASTED.** With no extra token configured there is exactly one voice and every single behaviour is the one the app had before this existed — held to that by its own regression tests. **(8) AND SAVING A TOKEN NO LONGER WIPES THE REST OF THE SETTINGS**: `Set-Grinder-Token.bat` used to overwrite the whole settings file, so a second run silently discarded the server id and all four channel ids and the bot came back half-broken with nothing in the log. Both token scripts now edit one line, keep the rest, and genuinely hide the token as it is typed. **What is NOT proven: that audio comes out of the second identity.** That needs the founder's own token and their own ears — the tests cover every decision, never the sound. _(Zuko goodnight run, 2026-08-12 night 3.)_

## The two features (frozen scope)

1. **The Mix (offline):** two picked catalog songs — Song 1 (beat) + Song 2 (vocals) — become one finished, continuous track with Song 2's vocals arranged _like a DJ_ over Song 1's instrumental (vocals enter on drops/choruses, the beat sometimes drops out for a breath, Song 1's own vocal sometimes kept for contrast, everything on the beat). Not a flat paste.
2. **Instant Changes (live) + Regenerate:** while the mix plays, short typed commands land on the next beat; a Regenerate button produces a different valid take.

## Screen 1 — Pick your two songs ✅ built (curated catalog — MVP pivot 2026-07-06)

- **Purpose:** get the raw material in — **from a curated catalog, not uploads** (founder decision 2026-07-06: users kept hitting "tempos too far apart" from misread/incompatible uploads, so the MVP preloads hand-verified songs where **every pairing blends by construction**).
- **On it:** two song slots — "Song 1 → its beat" and "Song 2 → its vocals". Clicking a slot opens a **dropdown of the preloaded songs for that role only** — Song 1 lists only beat songs, Song 2 only vocal songs (filtered by each catalog entry's `role_hint`). Each song is pre-analyzed and tempo-verified once by us. **No prompt box** (it steered nothing at mix time — live steering happens on the Play screen, so it was removed to keep Setup clean).
- **Main action:** pick two songs → **Mix it**. _(2026-07-14, cap raised 2026-08-07: an optional **"Add another set"** lets you stack more pairs — **up to five mixes** per set (the core rule) — to play back-to-back as one continuous set; the running order shows on the right, reorderable/removable. Ignore it and this screen is unchanged. Sets can only be added here, not during playback.)_
- **Wider tempo reach now (movable master, 2026-07-08):** the app no longer needs both songs at nearly the same speed. When a pair is too far apart to force one onto the other, it meets them at a shared tempo — nudging the house track a little (protected: it barely moves, never dragged down) while the guest vocal takes the rest. This unblocked the founder's #1 pair, **Father Ocean × Tere Bina** (~143 vs 122 BPM, previously declined), now in the catalog and mixable.
- **Empty / error:** an empty catalog says "No songs in the library yet"; a failed catalog load says so plainly. No file-type errors anymore — there are no uploads.
- _(The upload flow still exists in the backend — it's how the operator ingests new catalog songs — but users never see it. "Uploads only" from the V1 table is superseded by this pivot for the validation MVP; open uploads may return post-validation, ideally with the tempo-fix control.)_

## Screen 2 — Studying your songs (the wait) ✅ built

- **Purpose:** honest progress while we split stems + analyze (~1 min first time, then cached).
- **On it:** friendly step checklist that ticks off in order — "splitting the vocals, drums & bass… finding the beat, key & structure… planning your arrangement". Reached automatically after **Make my mix**; the user presses nothing else. On any step failure: a plain-language message + a **Start over** button (never a crash or a dead end).
- **Order note (as-built):** stems are split _before_ analysis runs, because the beat/structure read uses the split vocal to find where the singer sings.
- **Edge:** low-confidence song (loose beat, unclear structure, non-Western key) → the planner then picks safer moves (see DJ Handbook Part 9 fallback ladder). _(Surfacing that note on this screen is a later polish.)_

## Screen 3 — Your mix (the heart)

> **⚠️ Superseded by the 2026-07-14 multi-set note above (branch `feat/multiset-ui`).** As of that change the Play screen has **no live steering** (Parts / chips / beat-up / command bar all removed) and instead shows the **set line-up** and plays the finished mix or the continuous two-set. The reshape-it-live description below is the pre-strip behavior, kept for history.

- **Purpose:** play the mix, show what the "DJ" decided, let the user reshape it.
- **On it:** play/pause; a simple timeline showing where Song 2's vocal enters and where the beat drops out (arrangement is visible, not a black box); the prompt/command bar; a **Regenerate ("give me another take")** button; an **Export** button.
- **Main actions:** play/pause; type a live command; regenerate; export.
- **Live command set (V1, lean):** "beat up" (drums/energy up), "take the bass out", "remove / bring back song two's vocals", "drop everything but the beat", "fade away". Each lands on the next beat/bar and answers back in DJ language ("dropping song two's vocal on the next bar").
- **Error / edge:** out-of-scope request ("add a third song", "make it sound like Drake", "change the lyrics", live BPM change) → polite decline that points to what V1 can do; a command with no clean runway → it waits for the next beat or does the closest clean move, and says so.

## Screen 4 — Export / share

- **Purpose:** get the mix out.
- **On it:** download the full mix, and a **short 15–30s clip** (the creator's native unit).
